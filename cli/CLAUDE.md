# inbox program

The `inbox` program serves the inbox to the person's browser, so they read and answer items outside Claude Code, and sets a session's progress from a long command that session runs.

- `inbox serve --data <mod.dataFolder>` serves the browser view on `127.0.0.1`, one copy per computer through the `program` job with `isService`, which cmod runs as a launchd agent or systemd user service whenever the person is logged in, and **Open in browser** opens the list or the shown item there. The browser view in `cli/src/app/` imports the pure parts of `src/items/`, as the terminal view does. Every rule and sentence both views show lives in `src/items/` once, `readingOf` and the fold and revision rules in `tree.ts` and the list rules, such as `queue` and `isArchived`, and `wording` in `item.ts`, so a view only draws.
- The server writes its port to `<mod.dataFolder>/server.json` through a temporary file and a rename, and reuses it on restart. Open in browser reads that file, and any server started on a data folder rewrites it, so a test server runs with `--data <scratch folder>`.
- `inbox progress [--data <folder>] [--session <id>] [<blocks JSON>]` sets a session's progress with no tool call, so a test run updates it as it runs. It writes `<data>/progress/<session>.json` itself, and no `changed`, through `setProgress` in `src/goals/progress.ts`, the function the `progress` tool runs, and never reaches the server's port, so it works while the service restarts. The session defaults to `CLAUDE_CODE_SESSION_ID`, which Claude Code sets in every Bash command, and the folder to `data/inbox` in `cmodStore`, the cmod store `cli/src/cmod.ts` names: `$XDG_DATA_HOME/cmod`, else `~/.local/share/cmod`. The blocks come from the argument, or from stdin without one. A bad block, no session or one that is not a session id, or a folder that does not exist exits 2 with the reason, and a failed write exits 1. `setProgress` alone checks the session id and the blocks, and `main.ts` turns its `Invalid` into exit 2. It checks the blocks against the `progress` tool's own JSON Schema, `progressInput` in `src/goals/progress.ts`, so a block the tool refuses exits 2 with the reasons the tool's refusal lists. The compiled program bundles that validator, `@cfworker/json-schema`, a dependency in the root `package.json`. A test runs it with `--data <scratch folder>`.
- The `program` job also has `isWebApp`, so cmod runs `tailscale serve` for the port and starts the server with `CMOD_TAILNET_NAME` and `CMOD_TAILNET_LOGIN`. The server still listens on `127.0.0.1` only, and `refusalOf` in `cli/src/server.ts` checks every request before any route runs. A `Host` name of `127.0.0.1` or `localhost` answers with no login. The `Host` name `CMOD_TAILNET_NAME` answers only when `Tailscale-User-Login` is `CMOD_TAILNET_LOGIN`. Every other request gets 403 with a one-line `error`. Tailscale picks its serve handler by the TLS server name and forwards the client's own `Host`, so a tailnet device can send `Host: 127.0.0.1`. Tailscale sets `X-Forwarded-For` on every request it forwards, so a local `Host` that carries it gets 403 too. Without the two variables, only the local names answer.
- The server provides `inbox/Goals` for every session on the computer, so another mod hears each goals and progress change without parsing the inbox's files. `goals(session)` answers that session's `Goals` and `Progress`, either of them absent, and `sessions()` answers the id of every session with a goals or progress file. `goalsReaderOf` in `cli/src/goals.ts` keeps both in memory, through `readGoals` and `readProgress` from `src/goals/`. It reads every goals and progress file it finds, with no running-session filter, because it answers for every session on the computer, where a mod reads only the files `loadsFilesOf` names. The server rereads both on each new mark its 500 ms poll of `changed` reads, and every `rereadMs`. A progress write writes no `changed`, so every poll with no new mark lists the `progress` folder's stamps through `readProgress` on the reader. The server tells `Change { session, part }` for each goals or progress file whose stamp, its `modifiedAt` and size, changed since the last read, after the reread, so a listener that calls `goals` gets the new file. `changed` holds only the last mark, so the stamps, not the mark, name what changed, and two writes between two polls tell two Changes. The reads run one at a time, so a poll and the timed reread never tell one write twice. A goals read that fails logs its error and keeps what it read before, as the mod's `loadGoals` in `src/actions.ts` does, so it never stops the server from starting or the browser view from hearing items, and the next read that succeeds tells what changed.
- The program also tells `Change { session, part: 'goal' }` for each `cmod/Sessions` `Change` with `part: 'goal'` on this computer, so the mod in every session hears another session's goal change. In `@cmodjs/core` 8.3.1, session code's `providers('cmod/Sessions')` never lists this computer's `cmod serve`, while a program's `connection.listen` reaches it, because `cmod serve` answers `cmod/Sessions` itself. `relayGoalChanges` in `cli/src/goals.ts` listens that way and tells the Change. The connection's `listen` takes no matcher, so it checks `part` itself. The goal text stays cmod's: a listener reads it with `goal.text()`.
- The interface's type is `types/index.d.ts`, which `.claude-plugin/plugin.json` names in `"types"`. A types file imports nothing, so it spells out the shapes `src/goals/` declares. `cli/tsconfig.json` includes it, and `goalsReaderOf` answers `InterfaceMethods<'inbox/Goals'>`, so `bun run --cwd cli check` fails when `src/goals/` drops a field the types file requires or gives a field a type the types file does not accept. TypeScript accepts extra fields, so a field added to `src/goals/` passes the check, and other mods do not see it until the types file names it. A field the types file marks optional passes too when `src/goals/` drops it.
- `main.ts` passes `provideGoals` from `cli/src/cmod.ts`, which runs `connect()`, then `provide`, then `relayGoalChanges`, only when `CMOD_MOD` is set, as `cmod program` sets it for the service. `serve` provides once the browser view listens, so a `cmod serve` that is not up yet never holds the browser view back. `inbox serve` run by hand provides nothing. A Bash command in a session that a cmod program started inherits that program's `CMOD_MOD`, so a test spawns `inbox serve` with no `CMOD_` variables, or it would connect to the person's `cmod serve`. A test checks the provider through `serve`'s `provide` option with a fake, and the relay through `relayGoalChanges` with a fake connection.
- The event stream sends each item as a `Summary`, every revision cut to its title, and the browser reads the shown item whole from `GET /api/items/:id`. Whole items made the first frame 3 MB, and Bun 1.4.4 stalls partway through one large stream write until the next write, which held a tab on "Reading the inbox…" for up to 30 seconds.
- `cli/build.ts` bundles `cli/src/app/` into `cli/build/script.txt`, `style.txt`, and `shell.txt`, which `cli/src/server.ts` imports `with { type: 'file' }`, so the compiled program embeds them. They end in `.txt` because TypeScript 7.0.2 has no types for `with { type: 'file' }`, and `@types/bun` declares `*.txt`. `shell.txt` names its build in the `inbox-build` meta, the SHA-256 of the script and styles, and the event stream's first frame names the build the server serves, so a tab on another build reloads itself.
- Bun 1.4.4 lets two servers that pass `development: false` share one port, so `cli/src/server.ts` passes `reusePort: false`, and a second copy finds the saved port taken and moves.
- `cmod link` builds the program from `cli/package.json`'s `cmod.build` and loads this checkout in every new Claude Code session. The root `tsconfig.json` leaves out `cli/`, so `bun run --cwd cli check` type-checks the program, and `bun test` runs every test file, `cli/tests/` included. cmod restarts the service on the new program a few seconds after each `cmod link` build or install of a new version, on the same port, so no one restarts it. A `bun` run of `cli/src/main.ts` checks nothing. A live browser check of code not yet linked runs its own server on a scratch `--data` folder.
