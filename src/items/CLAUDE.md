# Items

The items core holds what an item is, how it is stored, and every rule and sentence both views show, so the Sidebar and the browser show the same inbox.

- `src/items/` imports nothing from `@cmodjs/core`, which `tests/items.test.ts` checks. The store reads and writes through a `Disk`, and `repositoryOf` runs git through a `Run`. The mod passes cmod's `fs` and `process.run`.
- Both views show one list, `queue` in `src/items/item.ts`, newest revision first as mail apps list mail, and the Archive under it, `archive`, folded under one line until the person opens it: `session.isArchiveOpen` in the Sidebar, and component state in the browser, which opens it when the shown item is archived. `isArchived` is the one rule: an item is archived when it is closed, when a report delivers it, or open while `isFollowed` says no subscriber runs. Subscribers are the sessions delivery reaches, so the warning that no running session follows an answer, which also asks `isFollowed`, never disagrees with the Archive. It is computed from `Sender.isRunning` through `isRunning` and never stored, so an item comes back to the list when its session resumes, and a session whose running state the inbox has not read yet counts as running. An archived item still opens, and an open one still takes an answer, which reaches its session on resume. `cardStatusOf` names each row's status: changes requested, the closing word from `closedWord`, delivered, or agent closed. An unread row, `isUnread`, shows a dot and a bold title instead of a word, and a proposal, choice, or question, `needsAnswer`, shows its kind in the accent color, because it blocks an agent, while a report's kind is dim. `ofKind` filters both lists by the kind tab.
- A report's `delivers` front matter names the items its work finishes, which the `report` tool takes from the agent and checks: each id exists, and none is rejected or waiting on requested changes, because those decisions are still the person's. `deliveriesOf` in `src/items/item.ts` maps each delivered id to the earliest report that delivers it, from every item and never one scope, so a report filed by another session still delivers. A report delivers only the revisions before it, so an item revised after its report comes back to the list. It is computed and never stored on the delivered item, so no tool writes another agent's item file. `threadOf` gives an item's Delivered by and Delivers links, which both views draw, and `read` leaves delivered items out of its open list and names `deliveredBy`.
- An item stores only each writer's session id and agent type, never a title or color, because a session's title changes. `senderOf` in `src/items/item.ts` names the session from `Senders`, the current titles and running state cmod's sessions hold: the mod reads them with `sessions.list({ everyProject: true })`, and the server with `cmod sessions list --every-project --json`, which takes about 2.4 s, so both read them in the background, at load and every `rereadMs`. Both listings hold every session with its `isRunning`, so a session missing from them does not run.
- A files or api drawing draws as the /show-me tree, through `treeOf` in `src/items/drawings.ts`, and both views color each row by its `mark`.
- Each item is Markdown files, shared by every session on the machine: `<mod.dataFolder>/items/<id>.md` holds its latest revision, `revisions/<id>/<n>.md` each earlier one by the number people read, and `person/<id>.md` the person's notes, answers, and `lastRead`. A person file from 0.4 or older still holds `queuedAt`, which `parsePerson` ignores. `src/items/markdown.ts` writes each file and parses it back to the `Item` and `Person` types, and both views read only these files. A drawing is a `~~~` block, so a backtick-fenced code block in an idea is the idea's text, `#` lines included. Front matter values are written as JSON, which YAML reads too, and a plain YAML scalar a person types by hand, such as `kind: proposal`, reads as well. Only agents' tools write `items/` and `revisions/`, and only the person's views write `person/`. Neither lock-free writer can then erase the other's write. Inside one process the core runs every write through one `Disk` one at a time, but the terminal and the server are two processes. Each write also writes `<mod.dataFolder>/changed`, which every session watches with `fs.onChange`. Dozens of sessions run at once, so each one rereads only the files whose `modifiedAt` and size changed since its last read, in `items/` and `person/`, plus both files of the item `changed` names, and an item's `revisions/` only when its item file changed. cmod's `fs` has no delete, so an item stays in `items/` with its status, and the watch stays on one file however many items there are.
- Each stored item records its `format`, `format` in `src/items/markdown.ts`, in its front matter.
- Inbox 0.3.0 converted the JSON items of 0.2.0 and older to Markdown, and 0.4.0 reads only Markdown, so an older install updates through 0.3.0. `marksIn` in `src/items/heard.ts` still seeds both delivery marks from the one mark a session that ran 0.2.0 keeps in `session.heard`, so a long-running session never hears an answer twice. It goes once no session started before 0.3.0 runs.
- A stored revision index counts from 0, and `revisionNumber` in `src/items/item.ts` turns it into the number people and agents read, which counts from 1.
- `src/items/tree.ts` names each Problem, Solution, change, idea, and drawing by its path in the item, such as `p0.s.i1`, `p0.s.i1.d`, and `c0.d`, which keys the notes the person wrote, what changed since the revision they last read, and what a correction names. A fold is keyed by the path and the revision, because a path names a position that a revision can give to another part.
- `src/items/tree.ts` `revisedSince` matches parts between two revisions by what they say: Problems and Solutions by title, ideas by their words, the way a text diff aligns lines. Unmatched parts in one gap pair up as edits when they share at least half their words, and otherwise show as one removed part and one new part.
- A note on the whole item has the path `''`. The footer's Comment writes it, beside the answer buttons. Its new and changed badges, and what a revised item opens, come from it.
- The person file's `lastRead` is the newest revision the person has seen. Answering, moving the Inbox view to another item, and hiding it with `/inbox` set it, and in the browser view answering, moving to another item, and hiding or closing the tab. Next → opens the next item down the list, which marks this one read. Mark read on selected rows sets it without opening them.
- A plain Done on a report, with no words and no notes, reaches no agent, because a report is final and no agent waits on it. `isPlainDone` in `src/items/heard.ts` is the rule, and `isUnheard` asks it, so neither view warns that no session hears a plain Done. Done with a note still reaches the agent, because the note is a correction.
- `src/items/drawings.ts` imports beautiful-mermaid's TypeScript source, `src/ascii/index.ts`, which loads in 44 ms. The package entry also loads elkjs and takes 382 ms on every session start, and cmod refuses a dynamic `import()`. So `tsconfig.json` allows `.ts` imports, and `package.json` pins the exact version.
