# Goals

The goals core holds each session's requirements, tasks, and progress and how they are stored, so the mod in every session and the `inbox` program read the same files.

- Every session ever run leaves a goals file, so a load parses a goals file only for this session, each session `memory.senders` lists as running, and each session in `session.takenFrom`, whose file holds an active task this session owns, `loadsFilesOf` in `src/actions.ts`, and before the first listing only this session's and those in `session.takenFrom`. `rememberGoals` in `src/actions.ts` keeps `session.takenFrom` to that rule on each read and write, so `start` adds a session and closing the last such task drops it. `session.takenFrom` outlives a restart, so a task taken in a session that stopped stays in the gate. A tool that names another session reads that session's file when it runs: `start`, `finish`, `wait`, and `drop` through `updateGoals`, and `read` through `loadGoalsOf`.
- `memory.goalTexts` holds the goal text of each running session, read once when a listing first shows it running, and again only when a `Change` with `part: 'goal'` names it. A session that stops running leaves it. `hearGoalChanges` in `src/actions.ts` hears that `Change` two ways. In `@cmodjs/core` 8.3.1, session code's `providers('cmod/Sessions')` lists mods' providers and other devices' `cmod serve`, never this computer's, so it hears `cmod/Sessions` for other devices. It hears this computer's sessions through `inbox/Goals` from the mod's own `program` job's `provider`, which the `inbox` program relays from this computer's `cmod serve` (`cli/CLAUDE.md`). It listens once: `cmod serve` replays a mod's listeners onto a restarted program's provider. A session no Claude app shows, whose `surfaces()` is empty, such as `claude -p`, skips it, so it never starts the program. `onGoalChange` in `src/gates.ts` also updates this session's own text at once.
- The Goal and Tasks views keep their folds in `session.unfolded` and their open field in `session.openField`, never the Inbox view's `folds` and `editing`, which the Inbox view clears and `isWriting` reads.
- `progressInput` in `src/goals/progress.ts` is the one format of the progress blocks: the `progress` tool's JSON Schema in `src/schemas.ts`, and what `validateBlocks` checks for `inbox progress` and every progress file read. `validateBlocks` checks it with `@cfworker/json-schema` 4.1.1, the validator `@cmodjs/core` 8.3.1 bundles for tool input, set as cmod's `tool` sets it, so `inbox progress` refuses a block with the reasons the tool's refusal lists. It then checks by hand the three rules a schema cannot state: a bar's `done` is at most its `total`, each table row holds one cell per column, and a steps preset's `current` is at most its number of steps.
- The `progress` tool and `inbox progress` set a session's progress through `setProgress` in `src/goals/progress.ts`, which throws `Invalid` from `src/goals/store.ts` on a bad session id or block, and replaces `<mod.dataFolder>/progress/<session>.json` through a temporary file and a rename. It writes no `changed`, so a progress update wakes no inbox reload in any session. cmod's `fs` has no rename, so the tool renames with `mv` through `ran` in `src/actions.ts`, which the lock runs too. A session reads only its own progress file into `memory.progress`, which `rememberProgress` in `src/actions.ts` replaces only with this session's progress and never with one older by `at`: `followProgress` reads it at `setup` and each `loadAll`, and watches it with `fs.onChange`, moving the watch when the session id changes. cmod looks again for a watched path that was missing only every fourth check, so a session's first progress shows within 2 s and later ones within 0.5 s, and a test ticks the watch four times. `ProgressBlocks` in `src/components/progress.tsx` draws the blocks.
- A session's requirements and tasks live in `<mod.dataFolder>/goals/<session>.md`. `updateGoals` in `src/goals/store.ts` checks as `@inbox/goals/<session>.md` only the agent words that differ from the stored file's, a requirement's `capability` and `line`, a filing's `reason`, and a task's `title`, `evidence`, and `reason`, each word on its own, quotes and corrections left out, and runs no check when none differ. So `finish` checks the evidence and never the stored title, a `file` that only adds quotes runs no check, and a rule added after a word was stored never blocks a later write. It then writes the file and `changed` inside the lock folder `<file>.lock`, since other sessions' task tools write it too. It takes the lock before `inWriteTurn`, so a stale lock never holds item and person writes in the per-`Disk` queue. `changeGoals` passes a `Lock` that runs `mkdir`, `touch`, and `rm -d`, which cmod's `fs` lacks, and makes the lock's parent once per write. A writer takes the lock with `mkdir` and `touch`es its own random token in it, and releases it by removing that token, then the empty folder, so it never removes another writer's lock. A lock whose token, or whose empty folder, is older than 10 s is broken: the writer removes the stale token by its name, then the folder, and retries `take`. A fresh token stays in place, and a writer that finds the stale token gone removes nothing more. A failed release after the write landed is a warning, never a failure: a tool's answer carries it through `told`, and `changeGoals` toasts it for the person's actions. The person's actions and a full rulebook run skip the check. `parseGoals` refuses a task missing a field its `state` needs.
- `session.unfiled` holds the person's words not filed yet: each person prompt, which also sends a Note naming its id, each worded answer as `<item id>#<n>`, which its prompt names, and each goal change from a view as `view:<iso>`, which its prompt or Note names. A quote matches whole words and holds a letter or a digit.
- `src/gates.ts` listens on `sessions.current.goal`, which hears every agent, and tells them apart by the payload's `task`, or `turn.prompt.task` at a stop. A stop refuses each set of unfiled prompts and active tasks once per turn, and the refusal says the next stop passes. The next stop on the same set passes with no answer, so no session is trapped and a passed stop never keeps the agent working. A refusal and the `file` tool's quote error name each unfiled prompt by its id and its first line, cut to 120 characters by `firstLineOf`, and the session-start, compaction, and subagent notes keep the whole text. A subagent's note leaves out unfiled prompts. Notes quote each task's corrections.
- The gates, prompt filing, the turn-end refusals, and the checklist refusal, are added only when `sessions.current.surfaces()` is not empty, so a `claude -p` run or a background session files nothing and is never refused. `hasSurfaces` in `src/actions.ts` is that rule, and `deliver` asks it too, so there an answer's prompt asks for no filing and adds nothing to `session.unfiled`. The notes, the `start` links, and the hand-back run in every session.
- The main agent's note at any source but `compact` runs `loadAll` first, because cmod clears `memory` at `/clear`, `/resume`, and a fork, and runs `onSessionStart`'s `loadAll` alongside it. Other notes run `loadGoals`. An unreadable goals file is logged and left out of the note.
- cmod copies `session` state into a fork, and `/clear` resets it. `changeGoals` sets `session.goalsSession` to this session only while it is `null`, and `copyForkedGoals` in `src/actions.ts` moves it off a parent only after the copy lands, so only a fork names another session. `copyForkedGoals` copies that file's requirements and filings into this session's file, by id, before each load and each note reads it, so a fork keeps the person's words.
- `finish`, `wait`, and `drop` refuse a task another session took while `isRunning` in `src/items/item.ts` says that session runs, naming it. Any session closes a task whose owner no longer runs, so the requirements it serves can still be met. A planned task has no owner, so any session can make it wait or drop it.
- Add… and Reopen in the views tell the agent, as Correct… does: a Note during a turn and a Prompt between turns. Correct… on a task another session owns tells that session.
- `toastWaiting` in `src/gates.ts` toasts only the tasks of the files a load reads, and a file it sees for the first time, such as that of a session that just started running, toasts none of its tasks, as the first load does.
- A tool's `execute` never learns which agent called it, so `goal.beforeToolCall` records a subagent's `start` with its `callId`, only when the payload has `task`, and `execute` consumes the record. The same call reaches the listener again with no `task`, so that never clears a record. The call's `onToolResult` clears it, so a `start` denied before it ran never links a later `start` of the same task. `onTaskEnd` clears what a subagent left, and `handBack` in `src/actions.ts` returns its active tasks to the main agent's gate. Each `load` and `loadAll` also hands back each active task this session owns whose `cmodTask` runs nowhere in `sessions.current.goal.tasks()` or a task's own `tasks()`, so a subagent that crashed, or ran before a restart, leaves no task stuck. A task with no `closedAt` runs while its `status` is running or absent.
- In cmod's test kit a fired `PreToolUse` runs the tool without the `beforeToolCall` listeners, so a test asks them with `raise.beforeToolCall(call, { task })`. A reload comes from the `every` tick, never the `changed` watch.
- The `ToolCall` and `ToolResult` styles in `src/mod.tsx` draw nothing for `mcp__inbox__progress` unless `isExpanded`, as in ctrl+o, so progress never shows in the chat. Claude Code folds a run of calls into one `ToolGroup` row, so the `ToolGroup` style unfolds a group that holds a progress call, which leaves no count line for the hidden call.
