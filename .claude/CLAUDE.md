# Inbox

The inbox mod holds every proposal, choice between options, product question, and report agents bring the person, across every running Claude Code session, and sends the person's answer back to each session that subscribed.

- `node_modules/@cmodjs/core/docs/` holds the docs of the installed `@cmodjs/core`. They match this version, and training data does not. Read the doc for the part you change, starting at `index.md`, before Claude Mod Manager (cmod) work.
- `tsc` reads `.claude-plugin/types/`, which Claude Code writes when it loads the mod. `cmod check` writes it when it is missing, so run `cmod check` before `tsc` in a fresh clone.
- The plugin is named `inbox`, so Claude sees its tools as `mcp__inbox__<tool>`. The repository is `claude-inbox`.
- The inbox holds items of four kinds: a proposal, options, a question, and a report. `src/items/item.ts` holds their types, and `src/items/store.ts` the store.
- `src/items/` is the core the terminal view and the web server share, so it imports nothing from `@cmodjs/core`, which `tests/items.test.ts` checks. The store reads and writes through a `Disk`, and `repositoryOf` runs git through a `Run`. The mod passes cmod's `fs` and `process.run`.
- An item's status is `open`, `answered`, or `withdrawn`: the person's answer or the agent's withdrawal, whichever came first. An open item is with an agent while a correction answers its current revision, so the agent's next revision ends the wait without any status change. A closed item stays in both views under Closed, marked by `closedWord` in `src/items/item.ts`, and opens with its answer and no actions.
- An item stores only each writer's session id and agent type, never a title or color, because a session's title changes. `senderOf` in `src/items/item.ts` names the session from `Senders`, the current titles cmod's sessions hold: the mod reads them with `sessions.list({ everyProject: true })`, and the server with `cmod history sessions --all --json`, which takes about 2.4 s, so both read them in the background. Stored items from before still hold a `title` and `color`, which nothing reads.
- A files or api drawing draws as the /show-me tree, through `treeOf` in `src/items/drawings.ts`, and both views color each row by its `mark`.
- Each item is two JSON files, shared by every session on the machine. Only agents' tools and the format-6 migration write `<mod.dataFolder>/items/<id>.json`, and only the person's views write `<mod.dataFolder>/person/<id>.json`, which holds the person's notes, answers, `lastRead`, and `queuedAt`. Neither lock-free writer can then erase the other's write. Inside one process the core runs every write through one `Disk` one at a time, but the terminal and the server are two processes. Each write also writes `<mod.dataFolder>/changed`, which every session watches with `fs.onChange`. Dozens of sessions run at once, so each one rereads only the files whose `modifiedAt` and size changed since its last read, in both folders, plus both files of the item `changed` names. cmod's `fs` has no delete, so an item stays in `items/` with its status, and the watch stays on one file however many items there are.
- cmod's `switchSession` resets `memory` at `/clear`, `/resume`, and a fork without rerunning `setup`, so `load` rereads every file at each session start.
- Before format 6, an item file held the person's fields and `mod.state.global.notes` held the notes. Every setup moves each item file below format 6 into its person file, adds any answer a session on the old release wrote after an earlier move, and rewrites the item file at the current format, so the old release skips it. That move, its rewrite of `items/`, the seeding of two delivery marks from one, and `global.notes` go away in the next release.
- An agent never writes a format. `src/schemas.ts` is the format: each tool's JSON Schema requires every field the person needs.
- A Problem and a Solution are lists of ideas, each with an optional drawing under it. A report is not: it holds a list of `changes`, each one sentence with an optional drawing and short evidence, plus the Problems left `open`. An agent declares drawings, and `src/completion.ts` checks each one against the code and completes it with `trace api` (at `HEAD` too, for a report's old signatures) and, for each file of a report, `git diff HEAD`, and draws each Mermaid diagram as text with `drawnDiagram` in `src/items/drawings.ts`, before the item is stored. Paths are relative to the item's `project`: the folder the agent's session started in, or the repository it names. The stored drawing is what the code held when the agent filed it. It also refuses a Solution with no drawing.
- beautiful-mermaid lays branches side by side and has no width limit, and the Sidebar has no horizontal scroll. So `src/components/drawing.tsx` draws the stored boxes only when they fit the page's `columns`, and otherwise an outline it builds from the Mermaid source with beautiful-mermaid's parsers.
- An item's text draws through `Prose` in `src/components/item.tsx`, which draws each list item with a • and its own `Markdown`. A markdown style cannot do it: cmod runs a mod's styles on every mod's `Markdown`, and a style's `Default` draws with the enclosing element's key.
- Claude Code refuses a whole pane that draws two `Markdown`, `Input`, `Select`, `Client`, `Raster`, or `Image` elements with one string key, anywhere in its tree, and blanks the Sidebar. cmod's test kit checks it from 4.3.3. So each such key in an item holds the part's path, and the Answer box's key holds the item id.
- cmod gives a mod no call that moves the keyboard to an element. An `Input` drawn with `autoFocus` takes it when it appears in a page that holds the keyboard. So `a` on a question sets `session.editing` to the Answer box, which then draws with `autoFocus`, and an always-drawn `autoFocus` would take `x`, `m`, `n`, and `o` from the question.
- A stored revision index counts from 0, and `revisionNumber` in `src/items/item.ts` turns it into the number people and agents read, which counts from 1.
- `src/items/tree.ts` names each Problem, Solution, change, idea, and drawing by its path in the item, such as `p0.s.i1`, `p0.s.i1.d`, and `c0.d`, which keys the notes the person wrote, what changed since the revision they last read, and what a correction names. A fold is keyed by the path and the revision, because a path names a position that a revision can give to another part.
- The page shows one scope of items, kept in `session` state: this session's items by default, then this project, then every project. An item belongs to a session that filed it or follows it, and to a project by its repository, which `git rev-parse --git-common-dir` names, so every worktree of a repository is one project.
- `src/items/drawings.ts` imports beautiful-mermaid's TypeScript source, `src/ascii/index.ts`, which loads in 44 ms. The package entry also loads elkjs and takes 382 ms on every session start, and cmod refuses a dynamic `import()`. So `tsconfig.json` allows `.ts` imports, and `package.json` pins the exact version.
- The person file's `lastRead` is the newest revision the person has seen. Answering, moving the page to another item, and hiding the page with `/inbox` set it, and in the browser view answering, moving to another item, and hiding or closing the tab. Next → also sets its `queuedAt` to now, which puts the item behind the rest of the queue.
- A note on the whole item has the path `''`. The footer's Comment writes it, beside the answer buttons. Its new and changed badges, and what a revised item opens, come from it.
- `src/items/tree.ts` `revisedSince` matches parts between two revisions by what they say: Problems and Solutions by title, ideas by their words, the way a text diff aligns lines. Unmatched parts in one gap pair up as edits when they share at least half their words, and otherwise show as one removed part and one new part.
- The person picks every key, so the `toggle` hotkey declares no default combo and starts unbound until the person binds it in Settings. It runs the same show-or-hide as `/inbox`.
- A report is final: `revise` refuses it, and the next round of work is a new report.
- Each stored item records its `format`. `src/items/formats.ts` converts an item written in an older format when the store reads it, so an update never breaks stored items.
- The shown item, the scope, the folds, the note being written, and the file the File page shows live in `session` state, so a reload keeps the person's place.
- Tests check what agents receive, what the inbox refuses, and the stored data. The page's look is checked live, never by comparing drawn text.
- `src/links.tsx` restyles reply paragraphs and lists that link to an item file, so a click on the link opens the item in the Sidebar. Every tool answer gives the agent that link.
- Each session delivers its own messages. After every load and every 30 seconds, `deliver` in `src/actions.ts` sends this session a prompt for each answer the person gave and a note for each revision or withdrawal another session made, on the items it subscribes to, and records it in `session.heard` only after the send resolves, which Claude Code does once the prompt enters the conversation. Each item has one mark for its person file's answers and one for its item file's revisions and withdrawal, because a load can read one file before the other. A missing mark starts at `<mod.dataFolder>/delivering-since`, so the first start of a release sends no older answer.
- `src/pages/` holds the Inbox and File pages, `src/widgets/` the count above the prompt, and `src/components/` what the Inbox page draws with.
- `rules/inbox.md` tells Claude to bring proposals through the inbox, and `skills/proposals/` how to write each kind.
- `cli/` is the `inbox` program. `inbox serve --data <mod.dataFolder>` serves the browser view on `127.0.0.1`, one copy per computer through the `program` job with `singleInstance`, and **Open in browser** in an item's header opens the item there. The browser view in `cli/src/app/` imports the pure parts of `src/items/`, as the terminal view does. Every rule and sentence both views show lives in `src/items/` once, `readingOf` and the fold and revision rules in `tree.ts` and the page rules and `wording` in `item.ts`, so a view only draws.
- The server writes its port and token to `<mod.dataFolder>/server.json`, mode 0600, through a temporary file and a rename. Open in browser reads that file, and any server started on a data folder rewrites it, so a test server runs with `--data <scratch folder>`.
- `cli/build.ts` bundles `cli/src/app/` into `cli/build/script.txt`, `style.txt`, and `shell.txt`, which `cli/src/server.ts` imports `with { type: 'file' }`, so the compiled program embeds them. They end in `.txt` because TypeScript 7.0.2 has no types for `with { type: 'file' }`, and `@types/bun` declares `*.txt`. `shell.txt` names its build in the `inbox-build` meta, the SHA-256 of the script and styles, and the event stream's first frame names the build the server serves, so a tab on another build reloads itself.
- Bun 1.4.4 lets two servers that pass `development: false` share one port, so `cli/src/server.ts` passes `reusePort: false`, and a second copy finds the saved port taken and moves.
- `cmod link` builds the program from `cli/package.json`'s `cmod.build` and loads this checkout in every new Claude Code session. `cmod check` checks, type-checks, lints, and tests the mod but skips `cli/`, so `bun test` and `bun run --cwd cli check` cover the program. A running `inbox serve` keeps the build it started with after `cmod link`, so a live browser check of new code runs its own server on a scratch `--data` folder.
